# Midnight Chain & Wallet Integration

This document explains how Guess Who interacts with the **Midnight** blockchain
and crypto wallets. The core idea: the identity of your spy is committed
on-chain at game start, and your final guess is verified against that commitment
with a **zero-knowledge proof** — so the game can prove your guess was right (or
wrong) without ever revealing the spy until you declare.

For the gameplay rules themselves, see [gameplay.md](./gameplay.md).

## Wallets

The game connects to Midnight-compatible browser wallet extensions:

- **Lace** — via RDNS `io.lace.wallet` (or `window.midnight.lace`)
- **1AM** — via RDNS `network.1am.wallet` (or `window.midnight['1am']`)

Connection logic lives in `game/wallet.js` (`connectLace()` / `connect1AM()`),
with the connect UI and auto-reconnect in `game/scenes/MenuScene.js`.

How it works:

1. The game calls `walletEntry.connect('mainnet')`, which returns a
   `ConnectedAPI`.
2. It retrieves your **shielded address** via `getShieldedAddresses()`.
3. Your address and wallet choice are persisted in `localStorage`
   (`midnight_shielded_address`, `midnight_wallet_choice`) so the game
   auto-reconnects on reload.

Your shielded address is the identity used for the leaderboard, player stats, and
achievements. It is shown truncated in the UI (first/last few characters).

## The Smart Contract

The on-chain logic is written in Midnight's **Compact** language at
`contract/src/guess_who.compact`.

### Ledger (public) state

- `next_game_id: Counter` — auto-incrementing game ID.
- `games: Map<Uint<64>, Game>` — maps a game ID to `{ commitment: Bytes<32>,
  active: Boolean }`.

The `commitment` is a hash of the spy's identity and a random salt. It is public,
but reveals nothing about which character is the spy.

### Private state (witnesses)

Defined in `contract/src/witnesses.ts` as `GuessWhoPrivateState`:

- `culpritId` — the spy index (0–15)
- `salt` — a 32-byte random value

These are never published. They are only fed into the circuits as private
witnesses.

### Circuits

| Circuit | Purpose |
|---|---|
| `create_game()` | Computes `commitment = hash(culpritId, salt)`, increments `next_game_id`, stores the game, and discloses the new `game_id`. |
| `submit_guess(game_id, guess_id)` | Recomputes the hash from the private witnesses, asserts it equals the stored commitment, then compares `culpritId == guess_id` and discloses the boolean result. Marks the game inactive when correct. |
| `delete_game(game_id)` | Optional cleanup of completed games. |

The commitment-then-reveal pattern is what makes the game trustworthy: the spy is
locked in at game creation, and the proof guarantees the answer at declare time
matches that exact commitment.

## On-Chain Game Lifecycle

The server (`server/src/`) sponsors the on-chain interactions so players don't
need funds.

1. **Pre-generation (pool).** A background `poolWorker.ts` keeps a pool of
   ready-to-play games. Each runs the `create_game` circuit and stores
   `game_id`, `culprit_id`, `salt`, and `contract_address` in the `game_pool`
   table. Target pool size is configurable via `POOL_TARGET_SIZE`.
2. **Session start** (`POST /api/session/start`). Claims a pre-generated game
   from the pool (or creates one on demand) and returns the `sessionId`,
   `characters[]`, `contractAddress`, and `gameId` to the client.
3. **Questions** (`POST /api/question`). Answered **off-chain** by the server —
   no transaction involved.
4. **Declare** (`POST /api/declare`). The server builds the private state
   (`{ culpritId, salt }`) and runs `submit_guess(gameId, guessId)`, signs the
   transaction, submits it to the chain, and returns `{ correct, txId }`.
5. **Score** (`POST /api/scores`). Records the leaderboard entry and awards any
   achievements.

## DUST Coin & Transaction Fees

Midnight transaction fees are paid in **DUST** (distinct from NIGHT).

- The server wallet holds DUST to **sponsor** player declare transactions.
- DUST is generated from NIGHT UTXOs via
  `registerNightUtxosForDustGeneration()`; the server registers UTXOs and waits
  (~5–15 min) for dust to accrue, checkpointing progress so it survives
  restarts.
- `GET /api/dust` reports `{ available, pending, availableCoins, pendingCoins }`.

### Single-coin queueing

The server typically holds a **single DUST coin**, so only one transaction can
be in flight at a time. `server/src/onChainQueue.ts` implements a semaphore that:

- serializes on-chain transactions, and
- **prioritizes a player's declare** over background pool refills.

This is why **pool refill pauses during active game sessions** — to keep the DUST
coin free for the player's declare transaction.

## Proofs

- Zero-knowledge proofs are generated by a **proof server**.
- By default proofs are generated **server-side** (sponsor), but
  `GET/POST /api/proof-server` can toggle to client-side proof generation for
  development.
- Compiled ZK artifacts (prover/verifier keys, ZK IR) are produced by compiling
  the contract and served from `public/managed/guess_who/`.

## Environment Variables

**Required:**

- `WALLET_SEED` — server wallet seed (64-char hex or BIP39 mnemonic)
- `GUESS_WHO_CONTRACT_ADDRESS` / `VITE_CONTRACT_ADDRESS` — deployed contract
  address (auto-deployed if blank)
- `VITE_API_URL` — server URL (default `http://localhost:3001`)

**Optional:**

- `POSTGRES_URL` — Postgres connection (falls back to in-memory storage)
- `POOL_TARGET_SIZE` — target pre-generated pool size
- `PROOF_SERVER_URL` — override the proof server URL

## Data Storage

Game data is stored in PostgreSQL (in-memory fallback if `POSTGRES_URL` is
unset), initialized in `lib/db.ts`:

- `sessions` — active game sessions (`spy_id`, `salt`, `characters`, 30-min TTL)
- `game_scores` — per-game results for the leaderboard
- `game_pool` — pre-generated on-chain games
- `player_stats` — per-address `spies_caught` / `games_played`
- `player_achievements` — one row per address per unlocked achievement
